# REST vs GraphQL · 모션 스토리보드

structure: single-flow (scenes: trips → shape → whatif → cost → verdict)

질문: "글 상세 화면 하나를 그릴 때 REST와 GraphQL은 무엇이 다른가?" 의도는 **비교**(A vs B)이고, 뒤에 "필요한 필드 수를 바꾸면?"이라는 **trade-off** 하나가 붙습니다.
모델: 화면이 필요로 하는 필드를 1~8개로 놓고, REST는 리소스(엔드포인트) 단위로, GraphQL은 필드 단위로 받는다고 봅니다. 바이트 수는 JSON 길이를 어림한 단순 모델이고 화면에도 그렇게 적습니다. trips·shape 장면은 기본값 n = 4의 이야기를 고정해서 보여 주고, whatif 장면에서 n을 움직입니다.

## 단순 모델

필드 순서(화면이 필요로 하는 순서 k)와 어느 리소스에서 오는지, 어림한 바이트:

| k | 필드 | REST 리소스 | B |
| --- | --- | --- | --- |
| 1 | 제목 | post | 48 |
| 2 | 본문 | post | 220 |
| 3 | 작성자 이름 | user | 24 |
| 4 | 댓글 본문 (3개) | comments | 210 |
| 5 | 아바타 | user | 52 |
| 6 | 댓글 작성자 (3개) | comments | 66 |
| 7 | 좋아요 | post | 14 |
| 8 | 댓글 시각 (3개) | comments | 90 |

- REST 응답은 엔드포인트가 정한 전체: `GET /posts/9` 352 B (id, title, body, authorId, likes, createdAt) · `GET /users/1` 180 B (id, name, avatar, bio, email) · `GET /posts/9/comments` 420 B (댓글 3개 × id, text, author, createdAt, likes).
- REST 왕복 수 = 필요한 필드가 걸친 리소스 수: n = 1, 2 → 1 · n = 3 → 2 · n ≥ 4 → 3. GraphQL 왕복 수 = 1.
- GraphQL 바이트 = 24 B(봉투) + 필요한 필드 합. REST 버림 = 받은 바이트 − 필요한 필드 합.

| n | 필요 | GraphQL | REST | REST 왕복 | 버림 |
| --- | --- | --- | --- | --- | --- |
| 1 | 48 | 72 | 352 | 1 | 304 |
| 2 | 268 | 292 | 352 | 1 | 84 |
| 3 | 292 | 316 | 532 | 2 | 240 |
| 4 (기본) | 502 | 526 | 952 | 3 | 450 |
| 8 | 724 | 748 | 952 | 3 | 228 |

n = 4에서 리소스별 버림: post 84 B · user 156 B · comments 210 B.

## concept 표

| concept | object | motion | meaning |
| --- | --- | --- | --- |
| 같은 요구 (need) | 머리글의 필드 칩 8개, 두 판, 구분선 | 두 판이 좌우에서 미끄러져 들어오고 구분선이 위에서 아래로 닦이며, 칩이 차례로 올라오되 필요한 4개만 색이 차고 나머지는 점선으로 남는다 | 두 방식에 주는 입력은 같다: "이 화면은 이 필드들이 필요하다" |
| 왕복 (trip1~3) | REST 요청·응답 알약, 엔드포인트 줄, 왕복·받음 카운터 | 요청 알약이 화면에서 서버로 건너가 엔드포인트 줄을 켜고, 응답 알약이 되돌아오면 왕복 카운터가 1 오르고 받음 바이트가 리소스 크기만큼 굴러 오른다 | REST는 리소스마다 왕복이 하나씩 필요하다 (under-fetching) |
| over-fetching (trip1~3, overfetch) | REST 응답 줄의 필드 칩 (6·5·5개) | 응답이 도착하면 칩이 차례로 펼쳐지고 쓰는 칩만 색이 찬다; overfetch에서 REST 판에 초점이 모이고 안 쓰는 칩 위로 취소선이 그어지며 옅어지고, 버림 바이트가 0에서 450까지 굴러 오른다 | 엔드포인트가 모양을 정하므로 안 쓰는 필드도 받아서 버린다 |
| 서버 쪽 조합 (trip1~3) | GraphQL 리졸버 줄 post → author → comments, 왼쪽 세로 막대 | 요청 알약이 한 번 건너간 뒤 리졸버 줄이 왕복마다 하나씩 켜지고 왼쪽 세로 막대가 1/3씩 채워진다 | REST가 왕복으로 하던 조합을 GraphQL은 서버 안에서 한다 |
| 정확한 모양 (trip3, exact) | GraphQL 응답 알약, 응답 카드, "요청한 모양 그대로" 구절 | 마지막 리졸버 뒤 응답 알약이 한 번 돌아오고 요청한 필드만 담긴 카드가 줄 단위로 조립된다; exact에서 GraphQL 판에 초점이 모이고 구절 위로 형광펜이 지나가며 버림 0 B 카운터가 한 번 커졌다 돌아온다 | 왕복 1번, 버리는 필드 0 |
| 쿼리 = 응답 (mirror) | 쿼리 줄 4개, 응답 줄 4개, 그 사이 연결선 4개 | 매치컷으로 커진 응답 카드 옆에 쿼리 카드가 올라오고, 연결선이 쿼리 줄에서 응답 줄로 차례로 뻗어 나가며 짝이 되는 응답 줄이 밝아진다 | 응답의 모양을 정하는 쪽은 쿼리를 쓴 클라이언트 |
| 엔드포인트 = 모양 (endpoint) | REST 응답 카드 3장의 안 쓰는 필드 칩, "버림 N B" 배지 | 카드 3장이 차례로 올라오고 안 쓰는 칩 위로 취소선이 차례로 그어지며 카드마다 "버림 84 / 156 / 210 B" 배지가 튀어 오른다 | 서버가 정한 모양이 그대로 오니 버리는 줄이 생긴다 |
| 수치 모델 (model) | 필드 칩 8개, 왕복·바이트 막대와 숫자, 리소스 사다리 | 막대가 0에서 현재 n의 값까지 자라고 숫자가 같이 굴러가며, 필요한 리소스 칸이 차례로 켜진다 | 같은 화면이라도 필드 수에 따라 비용이 달라진다 |
| 줄일 때 (fewer) | 슬라이더 값 n, 칩, 막대, 숫자, 사다리 | n이 4에서 1로 내려가며 칩이 하나씩 꺼지고 GraphQL 바이트 막대는 필드마다 줄고 REST 막대는 3→2→1 왕복으로 계단처럼 꺾이며 사다리 칸이 꺼진다 | REST 비용은 리소스 단위로만 줄어든다 |
| 늘릴 때 (more) | 슬라이더 값 n, 칩, 막대, 숫자 | n이 1에서 8로 올라가며 REST 왕복이 n = 4에서 3에 닿아 멈추고 GraphQL 바이트만 계속 는다 | 화면이 풍부해질수록 왕복 이득은 고정되고 바이트 차이는 좁혀진다 |
| 캐시 (cache) | 브라우저→CDN→원본 레인 위의 두 알약, HIT·통과 배지 | REST GET 알약은 CDN에서 멈춰 HIT 배지를 띄우고 짧게 되돌아오고, GraphQL POST 알약은 CDN을 지나(통과 배지) 원본까지 갔다 온다 | URL 하나짜리 POST는 HTTP 캐시 계층을 활용하기 어렵다 |
| 복잡도 (complexity) | 서버 쪽 비용 칩 3개와 핵심 구절 | 칩이 차례로 올라오고 "서버의 복잡도" 구절 위로 형광펜이 지나간다 | 모양의 자유는 공짜가 아니라 서버 비용으로 치른다 |
| 결론 (verdict) | 결론 두 줄과 핵심 단어 | 두 줄이 가림막 뒤에서 차례로 올라오고 GraphQL·REST 단어 위로 형광펜이 지나간 뒤 보조 문장이 떠오른다 | 선택 기준은 왕복 비용과 모양의 자유 대 캐시와 단순함 |
